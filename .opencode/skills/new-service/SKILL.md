# Scaffold a new Go microservice

Create a new `ecommerce-<name>-service` that matches the existing services' architecture.
Read an existing service first (`ecommerce-catalog-service` for a write side, or a query
service for a CQRS read side) and mirror its structure. Do not invent new patterns.

## Decide the service shape first

- **Write side / source of truth** (like catalog): owns writes, emits Kafka events from an
  `outbound/kafka` producer, MongoDB repos in `outbound/mongo`.
- **Query side / read model** (like product-query, category-query): consumes Kafka events via
  an `inbound/kafka` consumer, projects into its own MongoDB read model. **Never** call the
  write service synchronously for data it should project from events.

## Directory layout to create

```
ecommerce-<name>-service/
  cmd/main.go                                 # fx composition root - no business logic
  internal/
    application/<aggregate>/
      <aggregate>.go                          # domain type
      create_<aggregate>.go                   # command handler (write side)
      get_<aggregate>.go / get_list_*.go      # query handlers
      repository.go                           # port interface
      errors.go
      event_factory.go                        # write side only
      mock_repository.go                      # generated by mockery
    infrastructure/
      inbound/connect/                        # Connect-RPC handlers
      inbound/kafka/                          # event consumers (query side only)
      outbound/mongo/                         # repo impls: *_entity.go + *_mapper.go
      outbound/kafka/                         # event producers (write side only)
    testutil/mocks/
  configs/config.standalone.yaml
  .mockery.yaml
  .golangci.yml
  Makefile
  VERSION
  Dockerfile
```

## Wiring conventions

- **Every package exposes `Module()` / `New*Module()` returning `fx.Options`.** Add components
  by providing them in a module, never by constructing them manually in `main.go`.
- **`cmd/main.go` assembles from `fx.Options` only.** Follow the existing order:
  commons modules (core, persistence, http, observability, messaging, validation, token) ->
  tenant modules -> domain/application/mongo/kafka -> connect. Copy the shape from
  `ecommerce-catalog-service/cmd/main.go`.
- **Multi-tenancy is pervasive.** Wire `ecommerce-commons/pkg/tenant` and the tenant-service-api
  consumer/provider/client modules. For tenant-scoped collections use
  `mongo.NewTenantRepository`; for non-tenant collections (e.g. outbox) use `mongo.NewRepository`.
- **Auth**: JWT via JWKS, config under `security.jwks`.
- **Config**: YAML under `configs/`, overridable by env/`.env`.

## Steps

1. Create the api repo too (`ecommerce-<name>-service-api`) if the service exposes RPCs or emits
   events: proto under `proto/<name>/v1/` (RPCs) and `proto/<name>/events/v1/` (events), then run
   `make generate`. Use the `release-api` skill when publishing the contract for production or CI.
2. Scaffold the service directories above, copying module boilerplate from the closest existing
   service.
3. Register the module in the root `go.work` (`go work use ./ecommerce-<name>-service`).
4. Add `.mockery.yaml` and run `make generate-mocks`.
5. Wire it into the local stack: add to `ecommerce-infrastructure` - a thin Helm chart under
   `helm/ecommerce-<name>-service/` (depends on `shared-helpers`), per-env values under
   `environments/*/values/`, register in the `Tiltfile` (`GO_SERVICES` with `api_deps`), and add
   to the prod `SERVICES` list in `environments/production/makefiles/deploy.mk`.
6. Run `make check-all` in the service to confirm deps, formatting, lint, tests, and vuln checks.

## Verify

- `make build && make test-unit` in the new service.
- `make run` starts and the Fx graph resolves with no missing-provider errors.
